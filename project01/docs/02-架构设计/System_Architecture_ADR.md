## ADR-001: 技术栈选择 - Java 21 + Spring Boot 3.x

### 决策背景

需要选择后端技术栈，考虑因素包括：
- 企业级稳定性和性能要求
- 团队技术经验和人才市场供给
- 生态成熟度和社区支持
- 与其他系统的集成能力

### 可选方案

| 方案 | 优点 | 缺点 |
|-----|-----|-----|
| Java 21 + Spring Boot 3.x | 生态成熟，性能稳定，企业级支持，社区活跃 | 启动较慢，资源占用较高 |
| Go + Gin | 性能优异，启动快，资源占用低 | 生态相对较小，团队经验不足 |
| Python + FastAPI | 开发效率高，AI生态完善 | 性能相对较差，并发能力有限 |
| Node.js + NestJS | 前后端统一语言，异步处理能力强 | 性能不稳定，不适合CPU密集型任务 |

### 决策理由

1. **企业级需求匹配**：本系统需要支持高并发、高可用的企业级场景，Java生态经过多年验证，稳定性有保障
2. **团队能力匹配**：开发团队拥有丰富的Java开发经验，学习成本低
3. **生态成熟度**：Spring Boot生态完善，有大量成熟的中间件和工具支持
4. **性能要求**：系统涉及AI模型调用，需要稳定的后端支撑，Java的JVM优化成熟
5. **技术栈一致性**：与现有企业系统技术栈保持一致，便于运维和集成

### 决策结果

采纳 **Java 21 + Spring Boot 3.2.x** 作为后端技术栈

## ADR-002: 数据库选型 - MySQL 8.0+

### 决策背景

需要选择关系型数据库，考虑因素包括：
- 数据一致性要求
- 事务支持能力
- 查询性能
- 运维成本和社区支持

### 可选方案

| 方案 | 优点 | 缺点 |
|-----|-----|-----|
| MySQL 8.0+ | 性能优秀，社区活跃，工具链成熟，主从复制完善 | 分表分库复杂度较高 |
| PostgreSQL | 功能强大，支持JSON和全文搜索 | 性能略逊于MySQL，运维成本较高 |
| SQL Server | 微软生态，工具集成好 | 商业授权，成本高 |
| Oracle | 企业级功能完善 | 授权费用高，运维复杂 |

### 决策理由

1. **性能与稳定性**：MySQL 8.0引入了大量性能优化，支持事务和ACID特性
2. **社区支持**：MySQL拥有庞大的用户社区，问题解决速度快
3. **运维成本**：MySQL部署简单，运维工具成熟，团队经验丰富
4. **扩展性**：支持主从复制、读写分离，便于水平扩展
5. **测试环境适配**：支持H2内存数据库进行单元测试，切换成本低

### 决策结果

采纳 **MySQL 8.0+** 作为生产环境数据库，**H2** 作为测试环境数据库

## ADR-003: 缓存方案选择 - Redis

### 决策背景

需要选择缓存方案，考虑因素包括：
- 数据访问模式
- 缓存命中率要求
- 分布式缓存支持
- 数据结构支持

### 可选方案

| 方案 | 优点 | 缺点 |
|-----|-----|-----|
| Redis | 支持多种数据结构，性能优异，集群方案成熟 | 内存占用较高 |
| Memcached | 简单高效，资源占用低 | 仅支持简单键值对，功能有限 |
| Caffeine | 高性能本地缓存 | 不支持分布式场景 |

### 决策理由

1. **数据结构支持**：Redis支持String、List、Hash、Set等多种数据结构，适合各种缓存场景
2. **分布式支持**：Redis Cluster提供成熟的分布式缓存方案，支持水平扩展
3. **性能要求**：Redis性能优异，能够满足高并发访问需求
4. **功能丰富**：支持过期策略、发布订阅、Lua脚本等高级功能
5. **团队经验**：团队对Redis有丰富的使用经验

### 决策结果

采纳 **Redis 7.x** 作为缓存方案

## ADR-004: 消息队列选择 - Kafka

### 决策背景

需要选择消息队列方案，用于异步任务处理（如LoRA训练），考虑因素包括：
- 消息吞吐量
- 消息可靠性
- 分布式支持
- 生态集成能力

### 可选方案

| 方案 | 优点 | 缺点 |
|-----|-----|-----|
| Kafka | 高吞吐，分布式，持久化，生态完善 | 部署和运维相对复杂 |
| RabbitMQ | 功能丰富，协议支持多，社区活跃 | 吞吐量相对较低 |
| ActiveMQ | 成熟稳定，支持多种协议 | 性能和扩展性有限 |

### 决策理由

1. **高吞吐需求**：LoRA训练任务需要高吞吐量的消息传递，Kafka在这方面表现优异
2. **分布式架构**：Kafka原生支持分布式部署，适合大规模场景
3. **消息持久化**：Kafka支持消息持久化，保证消息不丢失
4. **生态集成**：Kafka与Spring生态集成良好，便于快速开发
5. **社区支持**：Kafka拥有活跃的社区和丰富的周边工具

### 决策结果

采纳 **Kafka 3.6.x** 作为消息队列方案

## ADR-005: 文件存储方案 - MinIO

### 决策背景

需要选择文件存储方案，用于存储图像、模型文件等，考虑因素包括：
- 存储容量要求
- 访问性能
- 分布式支持
- API兼容性

### 可选方案

| 方案 | 优点 | 缺点 |
|-----|-----|-----|
| MinIO | 轻量级，兼容S3 API，分布式部署，开源免费 | 企业支持有限 |
| 阿里云OSS | 成熟稳定，功能完善，企业级支持 | 成本较高，云厂商锁定 |
| 本地文件系统 | 简单直接，成本低 | 扩展性差，可靠性有限 |

### 决策理由

1. **S3兼容性**：MinIO兼容S3 API，便于后续迁移到云存储
2. **分布式支持**：支持多节点部署，保证数据可靠性和扩展性
3. **轻量级**：部署简单，资源占用低，适合中小规模场景
4. **开源免费**：降低成本，避免厂商锁定
5. **功能完善**：支持版本管理、访问控制、生命周期管理等功能

### 决策结果

采纳 **MinIO** 作为文件存储方案

## ADR-006: 前端框架选择 - Vue 3

### 决策背景

需要选择前端框架，考虑因素包括：
- 开发效率
- 性能表现
- 团队经验
- 生态成熟度

### 可选方案

| 方案 | 优点 | 缺点 |
|-----|-----|-----|
| Vue 3 | 响应式设计，Composition API，学习曲线平缓 | 大型项目状态管理相对复杂 |
| React | 生态庞大，社区活跃，适合大型项目 | JSX学习成本，状态管理方案多样 |
| Angular | 功能完整，TypeScript原生支持 | 学习曲线陡峭，体积较大 |

### 决策理由

1. **开发效率**：Vue 3的Composition API提供了更好的代码组织方式，开发效率高
2. **学习曲线**：Vue语法简洁，学习成本低，便于团队快速上手
3. **性能优化**：Vue 3引入了响应式系统的重大改进，性能显著提升
4. **生态支持**：Element Plus提供了丰富的UI组件，便于快速构建界面
5. **团队经验**：团队拥有Vue开发经验，能够快速投入开发

### 决策结果

采纳 **Vue 3.4.x + Element Plus** 作为前端技术栈

## ADR-007: 认证方案选择 - JWT

### 决策背景

需要选择认证方案，考虑因素包括：
- 安全性要求
- 无状态设计
- 跨域支持
- 扩展性

### 可选方案

| 方案 | 优点 | 缺点 |
|-----|-----|-----|
| JWT | 无状态，跨域支持好，易于扩展 | Token过期处理复杂，需要刷新机制 |
| Session-Cookie | 成熟稳定，自动管理 | 跨域复杂，水平扩展困难 |
| OAuth2 | 标准协议，支持第三方登录 | 实现复杂，配置繁琐 |

### 决策理由

1. **无状态设计**：JWT不需要服务端存储会话，便于水平扩展
2. **跨域支持**：JWT通过Header传递，天然支持跨域请求
3. **安全性**：支持签名验证，防止token篡改
4. **扩展性**：便于集成OAuth2、SSO等认证方式
5. **生态支持**：Spring Security对JWT有良好的支持

### 决策结果

采纳 **JWT** 作为认证方案，配合Spring Security实现

## ADR-008: 授权方案选择 - RBAC

### 决策背景

需要选择授权方案，考虑因素包括：
- 权限管理复杂度
- 灵活性要求
- 可扩展性
- 与认证方案的集成

### 可选方案

| 方案 | 优点 | 缺点 |
|-----|-----|-----|
| RBAC | 角色层级清晰，管理简单，易于理解 | 灵活性有限，细粒度控制不足 |
| ABAC | 基于属性的访问控制，灵活性高 | 配置复杂，性能开销大 |
| ACL | 细粒度控制，权限精确 | 管理复杂度高，扩展性差 |

### 决策理由

1. **角色层级清晰**：系统只有三种角色（普通用户、设计师、管理员），RBAC能够很好地满足需求
2. **管理简单**：RBAC的角色-权限映射关系清晰，便于系统管理员管理
3. **易于理解**：开发和运维人员容易理解和维护RBAC体系
4. **集成性**：Spring Security原生支持RBAC，实现成本低
5. **扩展性**：可以在RBAC基础上扩展更细粒度的权限控制

### 决策结果

采纳 **RBAC（基于角色的访问控制）** 作为授权方案

## ADR-009: AI Provider 策略模式 + ComfyUI 集成

### 决策背景

需要为文生图和图生文提供多种 AI 模型支持，并集成本地 ComfyUI 作为高性能推理引擎，考虑因素包括：
- 支持多种 AI 提供方（云端 API + 本地部署），用户可自由切换
- ComfyUI 的 workflow 工作流模板机制需适配
- API 地址需支持运行时动态修改（管理后台配置）
- 异步生成场景下的结果轮询机制

### 可选方案

| 方案 | 优点 | 缺点 |
|-----|-----|-----|
| 策略模式 + Factory + Spring @Component | 解耦各 Provider，自动注册，易扩展 | 类数量较多 |
| 简单 if-else 分支 | 实现简单 | 违背开闭原则，扩展困难 |
| 消息驱动（每个 Provider 独立服务） | 隔离性好 | 架构过重，运维复杂 |

### 决策理由

1. **策略模式**：定义 `Text2ImageProvider` / `Image2TextProvider` 接口，各 Provider 通过 `@Component` 自动注册到 `AiProviderManager`，新增模型只需实现接口
2. **ComfyUI 集成方式**：封装为 `ComfyUIClient`（HTTP 客户端）+ `ComfyUIText2ImageProvider`（策略实现），通过 workflow JSON 模板 + 节点参数注入的方式生成图片
3. **运行时配置**：使用 `DynamicConfigService` 运行时切换 API 地址（DB 优先 → yml 兜底），修改即时生效无需重启
4. **条件创建**：`ComfyUIClient` 始终创建为 Bean，`isAvailable()` 根据 `ai.comfyui.enabled` 和连通性动态返回

### 决策结果

采纳 **策略模式 + Spring @Component 自动注册**，ComfyUI 作为独立 Provider 实现：

- `Text2ImageProvider` 接口：`ComfyUIText2ImageProvider`, `SiliconFlowText2ImageProvider`, `ZhipuText2ImageProvider`, `HuggingFaceText2ImageProvider`, `PollinationsText2ImageProvider`, `MockText2ImageProvider`
- `Image2TextProvider` 接口：`MockImage2TextProvider`, 以及云端 API 提供方
- 前端通过 `GET /api/ai/providers` 获取 Provider 列表和可用状态
- ComfyUI 默认 workflow 模板位于 `resources/workflow/comfyui_default.json`
